## 1. Паспорт приложения

**Название в Marketplace (display_name): «Yardi»**. Внутренний
app_id/папка: `yardi-connector`.

**Yardi Connector** — BYOK-коннектор к семейству из 7 SOAP-интерфейсов
Yardi Voyager ("Standard Interfaces"): Common Data, Billing & Payments,
Vendor Invoicing, Service Requests, Revenue Management, Lease Renewals,
ILS/Guest Card. Пользователь подключает свою собственную Voyager-
инсталляцию (её WSDL-эндпоинты + учётные Login-параметры + отдельный
InterfaceLicense на каждый нужный интерфейс). Imperal ничего не хостит
и не проксирует помимо самого SOAP-запроса.

**Сознательно вне охвата:** Store Web Services (SWS2, устаревший
ILS-листинговый интерфейс), RESO Web API/Data Dictionary (отраслевой
стандарт, не Yardi-специфичный), прямой SQL-доступ к базе Yardi.
Полная аргументация — `CONNECTOR_DISCOVERY.md` §6.

## 2. Проблема в человеческих словах

Когда **управляющая недвижимостью компания** сталкивается с
необходимостью **свести воедино данные из Yardi Voyager с остальным
рабочим стеком** (уведомления в Slack/PagerDuty о просроченных
платежах, автоматизация заявок на обслуживание, отчётность по
портфелю), ей приходится **вручную заходить в Voyager, экспортировать
CSV/отчёты, или ждать, пока штатный Yardi-интегратор напишет
кастомный SOAP-коннектор под конкретную задачу**, из-за чего возникает
**задержка в днях-неделях на каждую новую интеграционную идею и
отсутствие проактивных сигналов** (просрочка резидента, истекающий
договор, простаивающий юнит — узнают постфактум, а не заранее).

## 3. Кто пользователь и когда это включается

- Управляющий недвижимостью / property manager, использующий Yardi
  Voyager, у которого уже есть активная лицензия минимум на один из 7
  интерфейсов (лицензии продаёт сам Yardi, не Imperal).
- Триггер: "покажи мне отчёт по задолженностям", "какие договоры
  аренды истекают в следующие 60 дней", "заведи заявку на
  обслуживание для юнита X", "какие юниты сейчас пустуют".

## 4. Архитектурное решение (кратко, полное — в CONNECTOR_DISCOVERY.md)

SOAP-запросы строятся вручную (stdlib `xml.etree.ElementTree` +
`xml.sax.saxutils.escape`, БЕЗ `zeep`/`lxml` — портфель Imperal не
добавляет зависимостей за пределами `imperal-sdk`), с динамической
WSDL-интроспекцией на targetNamespace/soapAction (кэш в `ctx.cache` на
24 часа). Каждая операция несёт "Login-блок" (`UserName`, `Password`,
`ServerName`, `Database`, `Platform`, `InterfaceEntity`,
`InterfaceLicense`) внутри своего XML-тела — это ПОЛЯ запроса, а не
HTTP auth-заголовки, в отличие от остального портфеля.

Подключение хранится как одна запись на **клиента Yardi** (ServerName +
Database + Platform + UserName + Password + InterfaceEntity), с картой
`{interface_name: {wsdl_url, interface_license}}` внутри — пользователь
может подключить сколько угодно из 7 интерфейсов по одной и той же
Login-учётке, добавляя их по одному через `add_yardi_interface`.

## 5. Известное ограничение — честно зафиксировано

Не тестировано против живой Yardi-инсталляции (нет доступа к реальному
WSDL + InterfaceLicense) — см. `CONNECTOR_DISCOVERY.md` §8. Код и
модульные тесты валидны против документированного публичного контракта
(реальные имена операций и параметров из `yardi-sdk`). Это НЕ
технический блокер деплоя/публикации — блокером было бы отсутствие
кода/тестов/цен, а не отсутствие живого стенда, тот же прецедент, что
Iguana/IguanaX и Redox.
